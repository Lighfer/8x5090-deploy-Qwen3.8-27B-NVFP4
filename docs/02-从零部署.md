# 从零部署

以下步骤用于用户明确指定的新安装目录。维护已有生产机时先制定迁移方案，不能重装驱动、重启Docker或直接覆盖活跃目录。

所有大写Shell变量由本次用户提供。先按[环境输入](01-环境与边界.md)完成仓库外的`SITE_FILE`，不要给变量填入别人的环境信息。

## 1. 准备目标基础环境

只读检查GPU、Docker、Compose、NVIDIA运行时和目标目录：

```bash
nvidia-smi
docker version
docker compose version
docker info
```

目标必须已有合适的宿主驱动。若新机缺NVIDIA Container Toolkit，按其官方安装说明安装，再配置Docker运行时；Docker重启只可在用户确认无生产负载的新机执行。LXC需要宿主提供设备和LXCFS，不能在LXC内擅自安装另一套内核驱动。

基础环境按用户实际发行版选择官方步骤：[Docker安装](https://docs.docker.com/engine/install/)、[NVIDIA Container Toolkit安装与Docker配置](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)、[CUDA与驱动兼容性](https://docs.nvidia.com/deploy/cuda-compatibility/latest/)。源码工具需要Python3.11及以上、Git和curl，服务单元需要systemd；不把某台主机的软件包版本或安装命令当成通用前提。

确认模型父目录、模型目录、构建目录、部署目录与私有输入均位于仓库之外。确认磁盘和实际可用内存足够，授权GPU没有被其他业务占用。

## 2. 取得固定镜像和模型

```bash
python3 -B tools/fetch-platform-images.py --execute
python3 -B tools/build-stack.py --work "$BUILD_DIR" --prefix "$IMAGE_PREFIX" \
  --release "$RELEASE" --cpus "$BUILD_CPUS" --memory-gib "$BUILD_MEMORY_GIB" --execute
python3 -B tools/fetch-model.py --target "$MODEL_DIR" --execute
python3 -B tools/fetch-model.py --target "$MODEL_DIR" --verify-only
```

平台镜像按公开摘要下载。构建输出`$IMAGE_PREFIX:$RELEASE-runtime`和`$IMAGE_PREFIX:$RELEASE-router`，把实际引用填入本次环境文件；不覆盖旧标签。模型按18项固定文件的完整revision及SHA256下载，下载器的临时元数据不参与推理输入身份。

如果本次还要使用独立FP8模式，保留上述NVFP4输入作为回退，并对用户明确提供的第二个模型目录执行：

```bash
python3 -B tools/fetch-model.py --precision fp8 --target "$FP8_MODEL_DIR" --execute
python3 -B tools/fetch-model.py --precision fp8 --target "$FP8_MODEL_DIR" --verify-only
```

将该目录登记为外部环境文件的`paths.fp8_model_directory`；FP8锁文件固定78项公开输入，其中66个权重分片。未明确提供该目录时仍只生成原四种模式。FP8 KV静态尺度与首次GPU验收边界见[FP8独立部署方案](10-FP8独立部署方案.md)。

构建不启动模型，Rust、APT和Python构建依赖都留在临时容器和外部构建目录。网络受限时可使用工具明确支持的回环HTTP下载代理；不能关闭TLS、修改全局DNS或把代理凭据写入镜像。

## 3. 生成私有安装目录

初次`identity`三个编号均为0。先预览，确认后执行：

```bash
python3 -B tools/configure.py --site "$SITE_FILE"
python3 -B tools/configure.py --site "$SITE_FILE" --execute
cd "$DEPLOYMENT_DIR"
docker compose --env-file .env config --quiet
docker compose --env-file .env up -d --wait --wait-timeout 300 server
```

服务器和Worker使用固定2.3.0平台镜像。Compose只负责Server、Worker与固定入口，不直接启动P、D、Router或CPU缓存服务。

## 4. 网页创建真实资源

打开本次配置的管理地址。初始密码在控制服务的数据目录中，使用本次容器名读取：

```bash
docker exec "$SERVER_CONTAINER" cat /var/lib/gpustack/initial_admin_password
```

登录后按页面提示修改密码。密码不写入源码或公开报告。

1. 在资源中的集群页面添加自建Docker集群，使用本次环境文件填写的集群名称。
2. 添加节点，选择NVIDIA，检查驱动和容器运行时。模型父目录按本次输入挂载，宿主和容器路径保持一致。
3. 从最后生成的注册命令取得`GPUSTACK_TOKEN`，仅填入私有目录`.env`。不重复执行网页里的独立Worker容器命令。
4. 执行`docker compose --env-file .env up -d worker`，等待Ready，核对实际GPU及LXC内存报告。
5. 给Worker添加标签`node=本次调度标签值`，与环境文件的`names.worker_label`一致。Worker实际名称使用`names.node`，两者是独立输入，GPU选择器使用实际名称。
6. 在模型服务的YAML导入入口选择私有目录`pd-model-new-stopped.json`。JSON也是合法YAML；保持副本数0，先不绑定旧缓存编号。

读取真实编号，在外部环境文件登记后重新适配：

```bash
# 在源码仓库执行，DEPLOYMENT_DIR仍指向仓库外安装目录。
python3 -B tools/list-identifiers.py --deployment "$DEPLOYMENT_DIR"
python3 -B tools/configure.py --site "$SITE_FILE" --configure-only --execute
```

不要靠名字猜编号。生成器会保留已经填写的`.env`，同时更新模型查询、缓存集群、指标发现和各工具中的实际编号。

## 5. 安装入口、发现与指标服务

私有目录已生成Nginx初始上游，模型未就绪时入口返回503。使用私有目录中的服务单元安装到systemd；这些单元的工作路径已按本次目录生成：

```bash
cd "$DEPLOYMENT_DIR"
install -m 644 entrypoint/gpustack-legacy-api-sync.service /etc/systemd/system/
install -m 644 entrypoint/gpustack-legacy-api-sync.timer /etc/systemd/system/
install -m 644 entrypoint/gpustack-metrics-bridge.service /etc/systemd/system/
install -m 644 gpustack-pd-switch-recover.service /etc/systemd/system/
systemctl daemon-reload
docker compose --env-file .env -f compose.yaml -f compose.legacy-api.yaml up -d --no-deps legacy-api
systemctl enable --now gpustack-legacy-api-sync.timer
systemctl start gpustack-legacy-api-sync.service
systemctl enable --now gpustack-metrics-bridge.service
systemctl enable gpustack-pd-switch-recover.service
python3 -B apply-cache-provider-source.py --execute
```

本工具集面向一个受管理的单机模型入口；已有同名系统服务时必须先确认归属，不能覆盖其他安装。缓存提供方目录包含提前查询设置，首次启动模型前应用；升级GPUStack后应先比较新版目录，不能直接覆盖其他提供方更新。

## 6. 启动、验收后接业务

```bash
cd "$DEPLOYMENT_DIR"
./switch-pd.sh start --dry-run
./switch-pd.sh start --extended-check
./switch-pd.sh status
```

首次启动使用环境文件明确选择的方案；之后`start`记住上次成功方案。加载权重、编译、图捕获可能持续数分钟，不能只因短时间没有响应而重启。全部P/D/Router、实际参数、入口和内存检查通过后才恢复访问。

`--extended-check`会在入口隔离期间发送合成请求，并可通过模型重启核查CPU缓存读回；不能把它当成只读检查。目标机还需按业务要求验证小中大上下文、图片、工具、并发、长尾和失败恢复。运行记录只保存在私有部署目录。

仅做明确不发推理请求的维护时使用`--health-only`，它仍检查全部成员、真实参数和入口，但报告中必须保留未验证推理功能的边界。业务接入使用本次指定的推理地址，指标位于同入口的`/metrics`。
