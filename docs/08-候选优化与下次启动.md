## 配置调整

| 项目 | 候选行为 | 原因与失败行为 |
| --- | --- | --- |
| TP2通信 | 两卡配方移除`--disable-custom-all-reduce` | 官方实现支持两卡PCIe；四卡纯PCIe仍保留关闭。由vLLM做P2P检查，不设置跳过检查；不满足条件时沿官方路径退回NCCL |
| P/D的CPU及内存位置 | 有完整、已核验的`gpus.numa_nodes`输入时，给同节点角色增加`--numa-bind`和显式`--numa-bind-nodes`，保留`spawn` | 节点列表按实例内逻辑GPU序号和TP生成。多节点候选池或缺少映射时不绑定。绑定权限不足可退回只绑CPU；不能把拓扑检测失败当作可自动降级 |
| CPU共享池位置 | 只暴露本方案P显卡，启用`GPUSTACK_CACHE_CPU_AFFINITY=auto` | 新镜像Python启动钩子把缓存进程CPU限制在靠近P显卡且cgroup允许的集合；普通首次触碰分配有机会改善内存位置。不是严格内存绑定保证 |
| JIT缓存 | FlashInfer、CuTe DSL和CUDA使用候选版本独立目录 | 防止旧编译结果掩盖源码变更；旧目录保留供回滚。首次启动需重新编译，不能承诺与热启动相同的耗时 |

`/var/lib/gpustack/cache/`是GPUStack容器内数据目录约定，`/sys`是内核只读拓扑接口；它们不是主机安装位置。主机地址、路径、端口、卡号和镜像标签仍由本次外部输入提供。

CPU亲和性钩子默认关闭，只有缓存定义显式设置上述变量时执行。它只修改新进程自己的CPU允许集合，不改宿主机、现有进程、内存策略、设备映射或权限；无法识别拓扑时输出简短警告并保留原行为。

## 保留的调度及容量

| 方案 | 每个P并发 / 批预算 | 每个D并发 / 批预算 | P长请求阈值 |
| --- | --- | --- | --- |
| `1p1d-cache`、`1p1d-no-cache` | 12 / 16896 tokens | 24 / 1536 tokens | 1536，自适应 |
| `2p2d-cache` | 6 / 9216 tokens | 12 / 1536 tokens | 1536，自适应 |
| `1p2d-6gpu-cache` | 6 / 9216 tokens | 12 / 1536 tokens | 1536，自适应 |

仍为MTP3、默认xhigh、NVFP4 GPU KV、BF16 SSM、1536的KV与Mamba块、204800上下文、显存比例在2P2D为0.8714，其他方案仍0.84；图片预算64张、单张约100万像素；共享CPU容量由用户输入，只绑定P。日志统计间隔仍3秒。2P2D只把总显存预算适当增加约1GiB/卡，并发和批预算不变。该比例控制整个引擎的显存预算，最终KV池由运行分析确定，不能把增量直接当作KV容量增量；保留OOM检测和自动回滚。

P阈值调整为1536并保留自适应。原调度器重放显示：批预算9216时，三个各3072的长请求会耗尽预算，使等待队列无法检查缓存结果；1536在此竞争条件下留出准入机会。单请求仍可使用整轮预算，但更多分段可能增加调度成本，未据CPU验证承诺GPU性能。另加入不受计算预算限制的缓存结果推进，完整机制和验证边界见[缓存结果推进修复](09-缓存结果推进与分段.md)。

官方`numa_utils._is_auto_numa_available()`会在进程CPU亲和性受限或内存策略权限不足时跳过自动检测；`_get_numa_node()`随后在显式要求绑定且未给节点时抛错。因此LXC内不能仅加`--numa-bind`。环境文件的可选`gpus.numa_nodes`是GPU序号字符串到节点整数的完整映射，应逐卡读取PCI设备的`numa_node`，并与当前cgroup允许的CPU和内存节点核对。留空或省略时不启用P/D绑定。角色候选池跨节点时不同副本可能被分到不同节点，生成器不会猜测分配后套用固定列表。改变卡序、迁机和六卡切换都必须重新核对。CPU池亲和性钩子是独立功能，不能代替P/D拓扑配置。

## 下次启动及失败恢复

预备升级只更新私有安装文件与镜像锁，**不修改运行中的GPUStack模型定义**。当前容器继续使用原镜像。新镜像、新缓存定义和新配置在下次执行正式`start`或方案切换时一起应用。

```bash
# 当前目录为本次私有安装目录；严格排空，超时取消，不中断仍在服务的请求。
./switch-pd.sh start --require-drained --drain-timeout 600
./switch-pd.sh status
```

正式执行仍按隔离、排空、整组停止、释放旧缓存、创建新缓存、启动全部P/D/Router、核对实际参数和短时生成、恢复入口的顺序进行。成功才登记已应用。若首次应用失败，恢复原模型和缓存，验证后恢复原配置文件；备份损坏或发生其他维护修改时不覆盖未知内容，入口保持维护，沿用`recover`处理。

`next-start-release.json`只在私有目录记录版本、准备时boot ID、受管文件新旧散列、备份相对路径及状态。`prepared`表示仅已备好，`activating`表示正式事务已接管，`applied`表示验证通过，`failed-restored`表示失败后已恢复旧文件。旧镜像和旧编译缓存不能在此阶段删除。

可选的`gpustack-next-start.service`需要从生成结果安装并**只enable，不带`--now`**。下次开机先等已有恢复流程、控制服务、Worker和固定入口可完成预检。P/D可能不自动重启；若确认是新的开机周期、预备事务已绑定且本模型确实没有运行容器，则在入口隔离后接管旧实例记录，直接启动新版本，不必先加载旧模型。只要已有任何模型容器，就等待原服务可排空并严格核对队列。它不会在准备当晚自行切换，也不会启动人工停止的模型。原服务在事务接管前仍可能按旧版恢复并短暂接收请求；这些请求必须排空。若已有进程长时间不能恢复，自动应用停止，不能强行停止未知状态的请求。整个过程复用GPUStack公开接口，不直接修改离线数据库。

仅执行某个P/D容器的`docker restart`会沿用旧容器参数，不能使新镜像或新参数生效。应使用正式脚本；主机重启则依赖已安装并启用的上述服务。不可把“文件已更新”当作“运行容器已升级”。

## 实际验证边界

构建阶段不暴露GPU，限制CPU和内存，保持生产余量。镜像内检查旧修复仍在、新补丁13文件身份、Python语法，以及9项CPU逻辑：混合数值暂存、失败转换、缓冲轮换/扩容、混合KV视图复制、图片输入释放/恢复、调度确认进度与回退、参数包装移除、NUMA解析和CUDA未初始化。它们不证明GPU内核输出或性能。

隔离环境的启停测试覆盖正式切换、停止/启动、超时排空、缓存失败、模型失败、OOM、回滚失败后恢复、预备文件恢复、外部修改保护和开机保持停机意图。CPU测试和官方GPU回归是采用这些修复的依据；构建阶段不自动执行生产切换；实际GPU功能验收由维护窗口中的正式切换和扩展检查完成，证据保存在私有事务目录。不能据此推算未经对照验证的提速百分比。首次真正启用时由正式脚本做最低必要的就绪及生成功能检查，吞吐和高峰尾延迟仍需另外验证。
