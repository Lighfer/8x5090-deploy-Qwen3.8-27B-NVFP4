# 环境输入与使用边界

本仓库保存固定软件和可配置配方，不保存部署者的机器信息。AI每次开始工作都要先向本次用户询问环境；不能从示例、旧日志或历史部署推断真实值。

## 支持范围

参考配方面向Linux x86_64、RTX 5090/SM120、单机控制服务和Worker。提供LXC及普通Linux两种Compose输入。其他GPU、跨节点、不同模型和框架应单独验证；不能只改镜像名就宣称兼容。

目标需有可用驱动、Docker、Compose及NVIDIA Container Toolkit，能够让目标容器使用GPU。LXC的设备授权、驱动模块和LXCFS由宿主负责，不能在容器内替换宿主驱动。首先读取当前状态，不能对已有生产机照抄新机初始化操作。

构建使用固定CUDA运行环境。目标驱动与CUDA的兼容性应按目标环境和NVIDIA说明核对，不复制别人的驱动版本。主机软件、网络、磁盘、内存和GPU所有权都必须在实施前确认。

## 外部环境文件

将`config/site.example.json`复制到用户指定的仓库外私有文件，权限限制为仅本人或维护账号读取。示例全部为空值，资源编号初次准备明确填写0。

| 字段 | 含义与要求 |
| --- | --- |
| `host` | 实际IPv4地址、网络接口、`lxc`或`baremetal` |
| `paths` | 私有部署目录、模型父目录和完整模型目录；模型必须位于父目录下 |
| `ports` | 管理、推理、Worker API、Worker指标和动态端口段；互不冲突 |
| `names` | 项目、控制服务、Worker容器、代理、集群、Worker实际名称、独立调度标签值、模型、缓存及两个卷的名称；`node`与`worker_label`不必相同 |
| `gpus.eight_card_order` | 授权八卡的实际序号及顺序；前四张分配P，后四张分配D |
| `gpus.six_card_order` | 授权六卡的实际序号及顺序；前两张分配P，后四张分配两个D |
| `resources` | 用户选择的CPU缓存容量和最低空闲内存；不按物理宿主总量猜测 |
| `images` | 本次构建完成的运行、缓存运行和Router镜像引用；缓存镜像通常与运行镜像一致 |
| `identity` | 网页产生的实际模型、Worker、集群编号；初次准备为0，登记时必须为正整数 |
| `admin_user` | 实际GPUStack管理员用户名，不含密码 |
| `default_mode` | 用户明确选择的四种方案之一 |

八卡与六卡列表都必须无重复，六卡集合是授权八卡集合的子集。这里不假设可用卡从某个固定序号开始。TP2多副本角色在自己的四卡集合内调度，P/D集合互不重叠。

私有文件由用户保管，不提交，也不复制到源码目录。注册令牌随后填入私有部署目录的`.env`，不写入环境示例或公开报告。

## 软件参数与机器信息的区别

`recipes/`中的上下文、块大小、MTP、图像处理预算和参考并发数属于可复用的软件参数。主机地址、目录、卡号、资源编号、缓存容量和自制镜像ID属于每次部署的环境信息，只能在外部输入和生成结果中出现。

`/var/lib/gpustack`、Docker socket、Linux内核接口、镜像内部Python模块位置、构建容器的`/build`、代理容器的`/config`是上游或容器接口约定。它们不代表某台主机的安装目录，保留理由见[公开规范](07-公开审查与AI使用.md)。

## 生成和登记的保护

生成器拒绝仓库内输入、仓库内输出、根目录、符号链接、未知字段、端口冲突、重复GPU和猜测的初始资源编号。默认预览不创建目录；执行时先验证镜像存在，再写完整配置。

后续`--configure-only`只适用于生成器已登记且受管文件未被手改的目录；保留注册令牌和运行采集文件。遇到手改不能直接刷新散列把它掩盖，应先核对差异。

部署目录允许空格及中文，不能包含会触发systemd变量展开的美元符号。模型路径由JSON和Compose单引号环境值传递，不经过Shell拼接；常见空格、井号、引号和美元符号保留字面值。
